RPB Level 2
「実際に、どんなデータが返ってきたの？」
Returned Range 入門ドキュメント v0.2

============================================================
1. このドキュメントの目的
============================================================

Level 0では、

「MT5に過去データをお願いすると、何が起きるの？」

という疑問からRPB研究が始まったことを説明した。

Level 1では、

「では、どうやって確かめたの？」

という実験方法を説明した。

Level 2では、いよいよ実際の観測結果を見る。

ここでの問いはシンプルである。

「MT5に過去データをお願いしたとき、
実際には、どんなデータが返ってきたの？」

このLevelでは、Returned Rangeを中心に、
実際のAccess Resultを観測した内容を初心者向けに整理する。


============================================================
2. まず「返ってきたデータ」を見てみる
============================================================

MT5に過去データを要求すると、
条件によってデータが返ってくる。

そのとき、単に

「返ってきた」

だけを見るのではなく、

・何本返ったか
・最初のバーはいつか
・最後のバーはいつか
・どの時間範囲だったか
・要求した対象日時が含まれたか

を見る。

この「実際に返ってきた範囲」を、
RPBではReturned Rangeとして観測している。

Returned Rangeは、Returned First / Returned Last /
Returned Bars / Returned Spanなどから、
実際に返却されたデータの時間的な範囲を観測するものである。


============================================================
3. 「お願いした範囲」と「返ってきた範囲」は同じとは限らない
============================================================

ここが最初のポイントである。

たとえば、

「この日時から10本ください」

とお願いしたとしても、

必ずしも、

「そのまま10本返ってくる」

とは限らない。

実際の実験では、

RequestStart
RequestedBars

などの条件を変えることで、

ReturnedFirst
ReturnedLast
ReturnedBars
ReturnedSpan

が変化することを観測している。

つまり、

「何をお願いしたか」

と

「実際に何が返ってきたか」

は、別々に記録する必要がある。


============================================================
4. Returned Rangeを見るために、何を記録するのか
============================================================

Returned Rangeを観測するとき、
主に次の情報を見る。


【Returned First】

返ってきたデータの最初の日時。


【Returned Last】

返ってきたデータの最後の日時。


【Returned Bars】

返ってきた本数。


【Returned Span】

最初から最後まで、どのくらいの時間範囲だったか。


【rates[].time】

実際に返ってきた各バーの時刻列。


【Target Included】

要求したTargetが、
返ってきた範囲の中に含まれているか。


これらを組み合わせることで、

「どんな範囲のデータが返ってきたのか」

を具体的に観測できる。


============================================================
5. Boundaryの近くでは、返り方が変わった
============================================================

RPBでは、その時点で観測された
SERIES_FIRSTDATEを基準に、その前後を調べた。

ここでは、時間位置を細かく変えて、
Requestの結果を比較した。

今回のBoundary観測では、

-1秒 → Request Failure（4401）
 0秒 → Success
+1秒 → Success

という切り替わりが確認された。

つまり、Boundaryのすぐ近くでは、

「少し時間位置を変えただけで、
Requestの結果が変わる」

という現象を観測した。


============================================================
6. でも、0秒と+1秒で「返ってきた範囲」は同じだった
============================================================

ここが非常に重要である。

0秒でRequestが成功し、
+1秒でもRequestが成功した。

では、

「+1秒にしたことで、
もっと過去のデータが返ってきたのか？」

というと、今回のBoundary観測条件では、
0秒と+1秒のReturned Rangeは同じだった。

つまり、

Requestの成功／失敗が変化したこと

と

Returned Rangeが拡大したこと

は、同じ現象ではなかった。


============================================================
7. Returned Seriesも比較した
============================================================

RPBでは、Returned Rangeの
最初と最後だけを見るのではなく、

実際に返ってきたバーの時刻列も比較した。

Boundaryの0秒と+1秒では、
Returned Seriesが同一であることが観測された。

つまり、

・Returned Range
・Returned Series
・バー時刻列

を比較しても、
今回の条件では差が確認されなかった。


このことから、

「Requestが成功した」

という一つの情報だけでは、
返却データの構造まで十分には分からない。


============================================================
8. さらに細かく、1秒単位でBoundaryを調べた
============================================================

Boundaryの位置をさらに細かく調べるため、
B-3 Fine Boundaryでは、

-3秒
-2秒
-1秒
 0秒
+1秒
+2秒
+3秒

という1秒刻みの位置を観測した。

目的は、

「SERIES_FIRSTDATEの近くで、
RequestStartの位置によって
Returned Rangeの形成がどう変わるのか」

を確認することである。

B-3では1秒単位でBoundary位置を細かく調べ、
Returned Rangeの形成を観測した。

ここでも、Returned RangeとHistory Stateは
別々に評価した。

History Expansionを、
CopyRatesの成功だけから判断してはいない。


============================================================
9. RequestStartの位置を変えると、返ってくる位置も変化した
============================================================

B-8では、さらに細かく、

OffsetsSec
0, 59, 60, 119, 120秒

RequestedBars
1, 2, 3, 5, 10, 20

を組み合わせて観測した。

各条件を120回ずつ、
合計3,600回観測した。

この実験では、

RequestStartの時間位置に応じて、

・ReturnedFirst
・ReturnedLast
・ReturnedBars
・ReturnedSpan
・rates[].time

が段階的に変化することが観測された。

つまり、

「RequestStartを少し変えると、
返ってくるバーの範囲も変わる」

という関係を具体的に観測できた。


============================================================
10. 「10本ください」とお願いしても、10本とは限らない
============================================================

B-8では、

RequestedBarsを

1
2
3
5
10
20

と変化させた。

しかし、同じRequestStartの位置では、
RequestedBarsを増やしても、
取得本数に上限が生じることが観測された。

これは、

「要求した本数」

と

「実際に取得できた本数」

が別の観測値であることを、
具体的に示している。


============================================================
11. B-8では3,600回すべて成功した
============================================================

B-8の観測では、

3,600観測
すべてSuccess

となった。

成功率は100%だった。

しかし、この結果も、

「だから履歴が増えた」

という意味ではない。

同じ3,600観測を通じて、

SERIES_FIRSTDATE
SERIES_BARS_COUNT
SERIES_SYNCHRONIZED

には変化がなかった。

つまり、

Access Resultは得られたが、
History Stateの変化は観測されなかった。


============================================================
12. ここで「返ってきたデータ」と「履歴状態」がはっきり分かれる
============================================================

ここまでを見ると、次の二つが見えてくる。


【返ってきたデータ】

RequestStartやRequestedBarsによって、

・ReturnedFirst
・ReturnedLast
・ReturnedBars
・ReturnedSpan
・rates[].time

が変化することがある。


一方、


【MT5の履歴状態】

同じ観測の中で、

・SERIES_FIRSTDATE
・SERIES_BARS_COUNT
・SERIES_SYNCHRONIZED

に変化がない場合がある。


つまり、

「返ってきたデータが変わった」

ことと、

「MT5の履歴状態が変わった」

ことは、別々に観測できる。


============================================================
13. 以前の観測「RequestedBars=10で10本」はどう扱うのか
============================================================

ここでは、現在の結果と過去の観測が一致しない例も紹介する。

RPBには、過去に、

「RequestedBars=10で10本返った」

という観測が存在する。

しかし、その観測は、
現在の同じ条件・同じ環境では再現されていない。

このため、

「過去の観測は間違いだった」

とも、

「現在も必ず10本返る」

とも断定しない。

RPBでは、この過去観測を、

R-01
Non-Reproducible Observation

として保持している。

これは研究上重要な扱いである。

再現できない観測を、
都合よく消すのではなく、

「過去にはそういう観測があったが、
現在条件では再現できていない」

という状態のまま記録する。


============================================================
14. ここまでで分かった「Returned Range」の姿
============================================================

Level 2までで観測できたことを、
簡単にまとめると次のようになる。


① Request条件によって、
Returned Resultは変化する。


② RequestStartの時間位置によって、
ReturnedFirst / ReturnedLast / ReturnedBars / ReturnedSpan
などが変化する。


③ 実際に返ってきたバーの時刻列
rates[].timeも観測対象になる。


④ RequestedBarsを増やしても、
実際の取得本数に上限が生じる場合がある。


⑤ Boundary付近では、
RequestのSuccess / Failureが切り替わる。


⑥ Success / Failureが変化しても、
Returned Rangeが必ず拡大するわけではない。


⑦ Returned RangeやReturned Seriesが変化しても、
それだけでHistory Expansionとは判断できない。


============================================================
15. Level 2で、まだ分からないこと
============================================================

ここまでで、

「何が返ってきたのか」

については、かなり具体的に観測できるようになった。

しかし、

「なぜ、その範囲が返ってきたのか」

「そのRequestによって、
MT5内部の履歴がどう変化したのか」

「どの条件でHistory Expansionが起きるのか」

までは、まだ確定していない。


特に重要なのは、

Returned Range
        ↓
History Expansion

という単純な関係を、
今回の観測だけから認めることはできない、
という点である。


============================================================
16. Level 2のまとめ
============================================================

Level 0では、

「なぜ調べ始めたのか」

を説明した。

Level 1では、

「どうやって確かめたのか」

を説明した。

Level 2では、

「実際に何が返ってきたのか」

を見た。


そして、実際の観測から、

Request条件
    ↓
Access Result
    ↓
Returned First / Last
Returned Bars
Returned Span
rates[].time
Target Included
    ↓
Returned Range

という観測の流れが見えてきた。


同時に、

Returned Range

と

History State

は別々に観測しなければならない、
というRPBの基本原則も、
実際のEvidenceによって確認されてきた。


============================================================

Level 2では、
