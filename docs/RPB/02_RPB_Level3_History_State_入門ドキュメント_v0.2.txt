RPB Level 3
「では、そのときMT5の履歴状態はどうなっていたの？」
History State 入門ドキュメント v0.2

============================================================
1. このドキュメントの目的
============================================================

Level 0では、

「MT5に過去データをお願いすると、何が起きるの？」

という疑問からRPB研究が始まったことを説明した。

Level 1では、

「では、どうやって確かめたの？」

という実験方法を説明した。

Level 2では、

「実際に、どんなデータが返ってきたの？」

という問いから、Returned Rangeを見た。

Level 3では、ここから視点を一つ変える。

今回の問いは、

「そのとき、MT5の履歴状態はどうなっていたの？」

である。

ここでは、返ってきたデータそのものではなく、
MT5から観測できるHistory Stateを主役にする。

専門用語を覚えることが目的ではない。

まずは、

「実験の前と後で、MT5の履歴状態は変わったのか？」

を確認する。

これがLevel 3の入口である。


============================================================
2. Level 2までで分かったこと
============================================================

Level 2では、

Request
    ↓
Access Result
    ↓
Returned First / Last
Returned Bars
Returned Span
rates[].time
Target Included
    ↓
Returned Range

という流れを見た。

そして、

「返ってきたデータ」

と

「MT5から観測できる履歴状態」

は、別々に見る必要があることを確認した。

Level 3では、後者を詳しく見る。


============================================================
3. そもそも「履歴状態」とは何か
============================================================

ここでいうHistory Stateとは、

「MT5から見た、その銘柄・時間足の履歴が
その時点でどのような状態にあるか」

を観測するための情報である。

RPBでは、その代表として、

・SERIES_FIRSTDATE
・SERIES_BARS_COUNT
・SERIES_SYNCHRONIZED

を使っている。

これらは、Returned Rangeそのものではない。

Returned Rangeが、

「今回のRequestで何が返ってきたか」

を見るのに対して、

History Stateは、

「Requestの前後で、MT5から観測できる履歴状態が
どうなっていたか」

を見る。


============================================================
4. 3つの観測項目を簡単に見る
============================================================

【SERIES_FIRSTDATE】

MT5から、その時点で観測できるSeriesの最初の日時を見る。

RPBでは特に、

「実験前と実験後で、最初の日時が変わったか？」

を比較する。


【SERIES_BARS_COUNT】

MT5から観測できるSeriesのバー本数を見る。

RPBでは、

「Requestの前後で、履歴本数が変わったか？」

を比較する。


【SERIES_SYNCHRONIZED】

Seriesの同期状態を見る。

RPBでは、

「Requestの前後で、同期状態が変わったか？」

を比較する。


この3つを一緒に見ることで、

FirstDate
BarsCount
Synchronized

という3方向からHistory Stateの変化を観測する。


============================================================
5. Level 3では「前」と「後」を見る
============================================================

Level 3の実験構造はシンプルである。


【実験前】

History State
・SERIES_FIRSTDATE
・SERIES_BARS_COUNT
・SERIES_SYNCHRONIZED

        ↓

【Request】

過去データを要求

        ↓

【Returned Result】

・成功 / 失敗
・Returned Range
・Returned Bars
・Target Included

        ↓

【実験後】

History State
・SERIES_FIRSTDATE
・SERIES_BARS_COUNT
・SERIES_SYNCHRONIZED


ここで、

「データが返ったか」

と

「History Stateが変わったか」

を別々に比較する。

RPBでは、同じRequestについてこの二つを独立した観測結果として記録する。


============================================================
6. なぜ「返ってきた＝履歴が増えた」ではないのか
============================================================

Level 2で見たように、

Requestをするとデータが返ってくることがある。

しかし、

「データが返った」

という事実だけでは、

「MT5の履歴が増えた」

とは判断できない。

そのため、RPBでは、

CopyRates / CopyTimeの成功

と、

SERIES_FIRSTDATE
SERIES_BARS_COUNT
SERIES_SYNCHRONIZED

の変化を別々に記録する。

実験コードにも、

「CopyTime success does NOT imply History Expansion」

という観測ルールを明示している。

ここでいうHistory Expansionの判定は、
RPBが今回の研究で採用している観測基準である。

つまり、

Success
    ≠
History Expansion

である。


============================================================
7. 実際のEvidenceではどうだったのか
============================================================

ここから、実際の観測を見る。

C章では、

「何を変えればHistory Stateが変化するのか？」

を調べた。

C-1ではRequestStartの位置を変化させた。

C-2ではRequestedBarsを変化させた。

C-3では未ロード候補領域へのAccessを調べた。

C-4ではAccess Boundaryを細かく調べた。

C-5では、成功したAccessの後に
History Stateが変化するかを調べた。

これらはすべて、

「Request条件を変える」
→
「Returned Resultを見る」
→
「History Stateを見る」

という同じ観測思想で行われている。


============================================================
8. Boundary付近で見えたこと
============================================================

Boundary観測では、

SERIES_FIRSTDATEを基準にRequestStartを動かした。

今回のC-4観測条件では、

-1秒以前
    → CopyRates取得失敗

0秒
    → 取得不成立

+1秒以降
    → 取得成功

というAccess成立境界が観測された。

しかし、そのBoundary付近の観測では、

・SERIES_FIRSTDATEの変化なし
・SERIES_BARS_COUNTの変化なし
・SERIES_SYNCHRONIZEDの変化なし

だった。

つまり、

「Accessの成功／失敗が切り替わった」

ことと、

「History Stateが変化した」

ことは、同じ現象としては観測されなかった。


============================================================
9. RequestedBarsを増やしたらどうなったのか
============================================================

B-4では、

RequestStart
    -1秒 / 0秒 / +1秒

RequestedBars
    1 / 5 / 10 / 20

を組み合わせて観測した。

全1,440観測で、

・Success = 960
・Failure = 480
・FirstDateChanged = 0
・BarsChanged = 0
・SyncChanged = 0

だった。

また、今回のB-4条件では、+1秒位置でRequestedBarsを

1
5
10
20

と増やしても、代表結果ではReturned Rangeは1本に制約された。

ここでも重要なのは、

「要求本数を変えるとReturned Resultは変わり得る」

一方で、

「History Stateの変化は観測されなかった」

という点である。


============================================================
10. 成功したAccessの「その後」を調べる
============================================================

C-5では、すでに成功することが確認された領域の中で、

+1秒
+60秒
+600秒
+3600秒
+86400秒

をRequestStartとして観測した。

固定条件は、

RequestedBars = 10
Attempts = 120
WaitSeconds = 2秒

である。

全600観測について、

SuccessCount = 600
FailureCount = 0

そして、

SERIES_FIRSTDATE 変化 = 0
SERIES_BARS_COUNT 変化 = 0
SERIES_SYNCHRONIZED 変化 = 0
HistoryStateChange = 0

だった。

つまり今回の条件では、

「成功したAccessの後でも、
History Stateの変化は観測されなかった。」

という結果になった。


============================================================
11. ここで一つ大事な言葉が出てくる
============================================================

それが、

History Expansion

である。

RPBでは、

「History Expansionが起きたか」を観測する際、
単にRequestが成功したことや、
データが返ってきたことだけを使わない。

まず、

・SERIES_FIRSTDATE
・SERIES_BARS_COUNT
・SERIES_SYNCHRONIZED

などのHistory Stateに、
観測可能な変化があるかを見る。

これは、今回のRPB研究で採用している観測基準である。

今回のC章では、

これらの状態変化を伴うHistory Expansionは
観測されなかった。


============================================================
12. ただし「起きない」とは言っていない
============================================================

ここは非常に重要である。

今回の実験で、

History Stateの変化が観測されなかった。

だからといって、

「MT5ではHistory Expansionは絶対に起きない」

とは結論しない。

今回確認できたのは、

「今回試験した条件・対象・方法では、
History Expansionを示すHistory Stateの変化が
観測されなかった」

ということだけである。

History Expansionの実際の発生条件や、
内部で何がトリガーになっているのかは、
まだ確定していない。

また、過去のBoundary観測資料には、
0秒位置のAccess結果について異なる整理が存在するため、
その差異は別途、実験条件・実験版の違いを含めて確認する必要がある。


============================================================
13. Returned ResultとHistory Stateを並べてみる
============================================================

ここまでを一枚の図にすると、こうなる。


                 REQUEST
                    │
                    ▼
             ┌─────────────┐
             │ Access Result │
             └──────┬──────┘
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   Returned Result       History State
          │                   │
          ▼                   ▼
   Returned First       FIRSTDATE
   Returned Last        BARS_COUNT
   Returned Bars        SYNCHRONIZED
   Returned Span
   Target Included
          │                   │
          └─────────┬─────────┘
                    ▼
              前後を比較する


ここで、

Returned Result
        ≠
History State

である。

そして、

Returned Resultの変化
        ≠
History Expansion

でもある。


============================================================
14. RPBで見えてきた「二つの観測対象」
============================================================

Level 2とLevel 3を合わせると、

MT5へのRequestのあとには、
少なくとも二つの観測対象があることが分かる。


【観測対象A：返ってきたもの】

・Requestが成功したか
・何本返ったか
・どの日時が返ったか
・どの範囲が返ったか
・Targetが含まれたか

これはAccess Resultの世界。


【観測対象B：MT5の履歴状態】

・SERIES_FIRSTDATE
・SERIES_BARS_COUNT
・SERIES_SYNCHRONIZED

これはHistory Stateの世界。


この二つを分けることで、

「データが返った」

という現象と、

「MT5の履歴状態が変化した」

という現象を、
同じものとして扱わずに済む。


============================================================
15. ここまでで何が観測されたのか
============================================================

今回までのEvidenceから、少なくとも次のことが観測されている。

・Request条件を変えるとReturned Resultは変化し得る。

・Boundary付近ではAccessの成功／失敗が切り替わる。

・Boundary付近でもHistory Stateの変化は観測されなかった。

・RequestedBarsを増やしても、History Stateの変化は観測されなかった。

・成功したAccessの後でも、History Stateの変化は観測されなかった。

・したがって、今回の観測条件では、
  「Request成功 → History Expansion」
  という単純なモデルは成立しなかった。


============================================================
16. まだ分からないこと
============================================================

Level 3まで進んでも、まだ次の問いは残っている。

・History Expansionは、実際にはどの条件で起きるのか？

・History Stateを変化させるトリガーは何なのか？

・Access BoundaryとHistory Expansionには関係があるのか？

・Returned Rangeの変化とHistory Expansionには、
  どのような関係があるのか？

・MT5内部では、どのような処理が行われているのか？

これらは今回の観測だけでは確定できない。


============================================================
17. Level 3のまとめ
============================================================

Level 0では、

「なぜ調べるのか？」

を見た。

Level 1では、

「どうやって調べるのか？」

を見た。

Level 2では、

「何が返ってきたのか？」

を見た。

そしてLevel 3では、

「そのときMT5の履歴状態はどうだったのか？」

を見た。


その結果、

Returned Result
        と
History State

は、別々の観測対象として扱う必要があることが、
実際のEvidenceによってさらに明確になった。

そして今回の観測条件では、

Requestが成功しても、
Returned Rangeが変化しても、

History Stateの変化は確認されなかった。

だからこそ、次の問いが生まれる。

「では、History Expansionは、
いったい何をきっかけに起きるのか？」

ここから先が、

RPBの本格的な研究領域になる。
