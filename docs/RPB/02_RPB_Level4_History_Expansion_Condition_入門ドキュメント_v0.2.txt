RPB Level 4
「では、History Expansionは何をきっかけに起きるのか？」
History Expansion Condition 入門ドキュメント v0.2

============================================================
1. このドキュメントの目的
============================================================

Level 0では、

「MT5に過去データをお願いすると、何が起きるの？」

という疑問からRPB研究が始まったことを説明した。

Level 1では、

「では、どうやって確かめたの？」

という実験方法を説明した。

Level 2では、

「実際に、どんなデータが返ってきたの？」

という問いから、Returned Rangeを見た。

Level 3では、

「そのとき、MT5の履歴状態はどうなっていたの？」

という問いから、

・SERIES_FIRSTDATE
・SERIES_BARS_COUNT
・SERIES_SYNCHRONIZED

を中心にHistory Stateを観測した。

そしてLevel 3までで、一つの重要なことが見えてきた。

「Requestが成功した」
「データが返ってきた」

だけでは、

「History Stateが変化した」

とは言えない。

では、次の疑問が生まれる。

------------------------------------------------------------

「では、何を変えればHistory Stateは変わるのか？」

------------------------------------------------------------

これがLevel 4の入口である。

Level 4では、この問いを中心に、
History Expansionが起きる条件を探索する。

ただし、ここで先に答えを決めない。

「この条件ならExpansionする」

とは仮定せず、

「どの条件を変えたとき、何が観測されたのか」

を一つずつ確認していく。

これがRPBにおける
History Expansion Condition研究である。


============================================================
2. Level 3までのおさらい
============================================================

ここまでの研究を簡単に振り返る。

LEVEL 0
「なぜ調べるのか？」

        ↓

LEVEL 1
「どうやって調べるのか？」

        ↓

LEVEL 2
「何が返ってきたのか？」

        ↓

LEVEL 3
「MT5の履歴状態はどうだったのか？」

        ↓

LEVEL 4
「何がHistory Stateを変えるのか？」

である。

Level 2とLevel 3によって、

Returned Result

と

History State

は、別々の観測対象として扱う必要があることが明確になった。


============================================================
3. ここから「条件」を調べる
============================================================

Level 4では、

「Requestをした」

という一つの行動だけを見るのではなく、

Requestの条件を変える。

たとえば、

・どの位置からRequestするか
・何本要求するか
・どの領域へAccessするか
・Boundaryのどちら側から要求するか
・Access成功後にどうなるか

などである。

そして、その結果を、

1. Requestが成功したか
2. 何が返ってきたか
3. History Stateが変わったか

の順に見る。

重要なのは、

「返ってきたデータ」

と

「History State」

を最後まで分離することである。


============================================================
4. Level 4の基本実験モデル
============================================================

Level 4では、次のような考え方で実験する。


              条件を変える
                   │
                   ▼
                Request
                   │
          ┌────────┴────────┐
          ▼                 ▼
    Returned Result     History State
          │                 │
          ▼                 ▼
   何が返った？        何か変わった？
          │                 │
          └────────┬────────┘
                   ▼
              前後を比較


ここで、

Returned Resultが変わった

ことと、

History Stateが変わった

ことは、別々の結果として記録する。


============================================================
5. History Expansionとは何を調べるのか
============================================================

「History Expansion」という言葉を聞くと、

「MT5の履歴として観測できる範囲が広がること」

のように感じるかもしれない。

しかし、RPBでは、これを最初から確定した現象として扱うのではなく、
まず観測可能な変化を確認する。

具体的には、

・SERIES_FIRSTDATE
・SERIES_BARS_COUNT
・SERIES_SYNCHRONIZED

などのHistory Stateについて、

「Requestの前後で変化があったか」

を見る。

これは、今回のRPB研究で採用している観測基準である。

したがって、

Request成功
    ≠
History Expansion

である。

また、

Returned Rangeが変化した
    ≠
History Expansion

でもある。

Level 4では、この区別を維持したまま、
Expansionの条件候補を探索する。


============================================================
6. C-1 RequestStart
============================================================

最初に見るのは、

「どこを対象として要求するか」

である。

つまり、RequestStartを変える。

RequestStartの位置が変われば、

Returned Result

が変わる可能性がある。

しかし、ここで本当に知りたいのは、

「RequestStartを変えたことで、
History Stateも変わったのか？」

である。

そのため、

・SERIES_FIRSTDATE
・SERIES_BARS_COUNT
・SERIES_SYNCHRONIZED

をRequest前後で比較する。

今回のC章では、RequestStartを変化させた観測において、
History Stateの変化を示すHistory Expansionは確認されなかった。

これは、

「RequestStartでは絶対にExpansionしない」

という意味ではない。

あくまで、

「今回試験した条件では観測されなかった」

という結果である。


============================================================
7. C-2 RequestedBars
============================================================

次に、

「何本要求するか」

を変える。

RequestedBarsを変化させると、

Returned Result

が変化する場合がある。

しかし、

要求本数を増やした
    ↓
History Stateが増えた

とは限らない。

C-2の観測では、関連するEvidenceとしてB-4の結果も参照する。

実際、B-4では、

RequestStart
    -1秒 / 0秒 / +1秒

RequestedBars
    1 / 5 / 10 / 20

を組み合わせて、

全1,440観測を行った。

結果は、

・Success = 960
・Failure = 480
・FirstDateChanged = 0
・BarsChanged = 0
・SyncChanged = 0

だった。

また、今回のB-4条件では、
+1秒位置でRequestedBarsを

1
5
10
20

と増やしても、
代表結果ではReturned Rangeは1本に制約された。

つまり、

「要求する本数」

と

「実際に返ってきた本数」

は同じではなく、

さらに、

「要求本数を変えたこと」

と

「History Stateが変化したこと」

も同じではない。


============================================================
8. C-3 未ロード候補領域へのAccess
============================================================

次に、

「まだ履歴として読み込まれていない可能性がある領域へ
Accessしたらどうなるのか？」

を調べる。

ここで重要なのは、

「未ロード候補」

という言葉である。

この段階では、

「ここは確実に未ロードである」

と決めつけない。

観測上、

「未ロードの可能性がある領域」

として扱う。

そして、その領域へAccessしたとき、

・Requestは成功したか
・Returned Resultはどうなったか
・History Stateは変化したか

を確認する。

今回のC章では、
この条件でもHistory Stateの変化を伴う
History Expansionは観測されなかった。

したがって、

「未ロード候補領域へAccessすればExpansionする」

という単純なモデルは、
今回の観測からは成立していない。


============================================================
9. C-4 Access Boundary
============================================================

次に、Boundaryを見る。

Boundaryとは、ここでは、

「Requestが成立する側と、
成立しない側の境界付近」

として観測している。

Boundary付近では、

RequestStartを細かく動かすことで、

・失敗
・成功

が切り替わる位置を観測できる。

今回のC-4観測条件では、

-1秒以前
    → CopyRates取得失敗

0秒
    → 取得不成立

+1秒以降
    → 取得成功

というAccess成立境界が観測された。

しかし、そのBoundary付近でも、

・SERIES_FIRSTDATEの変化なし
・SERIES_BARS_COUNTの変化なし
・SERIES_SYNCHRONIZEDの変化なし

だった。

つまり、

「Accessの成功／失敗が切り替わる境界」

は観測できたが、

「その境界を越えたことでHistory Stateが変化した」

ことは観測されなかった。


============================================================
10. C-5 Successful Access後
============================================================

最後に、

「成功したAccessの後はどうなるのか？」

を見る。

C-5では、

+1秒
+60秒
+600秒
+3600秒
+86400秒

をRequestStartとして観測した。

固定条件は、

RequestedBars = 10
Attempts = 120
WaitSeconds = 2秒

である。

全600観測について、

SuccessCount = 600
FailureCount = 0

だった。

そして、

SERIES_FIRSTDATE 変化 = 0
SERIES_BARS_COUNT 変化 = 0
SERIES_SYNCHRONIZED 変化 = 0
HistoryStateChange = 0

だった。

つまり今回の条件では、

「成功したAccessの後でも、
History Stateの変化は観測されなかった。」

という結果になった。


============================================================
11. ここまでの結果を一度まとめる
============================================================

Level 4で調べた条件を並べると、

C-1
RequestStart
    ↓
History State変化なし

C-2
RequestedBars
    ↓
History State変化なし

C-3
未ロード候補領域へのAccess
    ↓
History State変化なし

C-4
Access Boundary
    ↓
History State変化なし

C-5
Successful Access後
    ↓
History State変化なし

となる。

各実験でReturned Resultには変化が観測されたものもあるが、
History Stateの変化は観測されなかった。

ただし、これは、

「どの条件でも絶対にExpansionしない」

という結論ではない。

正確には、

「今回試験した条件では、
History Stateの変化を伴うHistory Expansionは
観測されなかった」

という結論である。


============================================================
12. ここで研究として重要なこと
============================================================

もし、

「Requestした」
「データが返った」
「Boundaryを越えた」

というだけで、

「History Expansionした」

と判断してしまうと、

Returned Result

と

History State

を混同してしまう。

RPBでは、それを避ける。

たとえば、

Request
    ↓
Success
    ↓
Returned Bars = 1

という結果が出ても、

History State

・FIRSTDATE
・BARS_COUNT
・SYNCHRONIZED

に変化がなければ、

そこからHistory Expansionを推定しない。

逆に、

History Stateに変化が観測された場合には、

「何が変化したのか」

をさらに調べる必要がある。

つまり、Level 4は、

「Expansionを見つける」

だけではなく、

「Expansionと、それ以外の現象を分離する」

ための研究でもある。


============================================================
13. 現時点で分かったこと
============================================================

今回までのEvidenceから、

少なくとも次のことが観測されている。

・RequestStartを変えるとReturned Resultは変化し得る。

・RequestedBarsを変えるとReturned Resultは変化し得る。

・Boundary付近ではAccessの成功／失敗が切り替わる。

・Successful Accessそのものは観測できる。

・しかし、今回の試験条件では、
  それらに伴うHistory Stateの変化は観測されなかった。

・したがって今回の観測条件では、
  「Request成功 → History Expansion」
  という単純なモデルは成立しなかった。


============================================================
14. まだ分からないこと
============================================================

ここがLevel 4の重要なところである。

まだ、

「では、何ならHistory Expansionを起こすのか？」

が分かっていない。

残っている問いは、

・History Expansionが実際に発生する条件は何か？

・どのHistory State項目が最初に変化するのか？

・Request以外の操作が関係するのか？

・時間経過は関係するのか？

・Accessの回数は関係するのか？

・特定の履歴領域が関係するのか？

・BoundaryとHistory Expansionには関係があるのか？

・Returned Rangeの変化とHistory Expansionには
  どのような関係があるのか？

である。

これらは、今回のEvidenceだけでは確定できない。

したがって、ここから先は、

「条件候補を増やす」

だけではなく、

「何を変数として固定し、
何を変数として動かすか」

という実験設計そのものが重要になる。


============================================================
15. Level 4の現在地
============================================================

Level 4まで進んだことで、

RPB研究の観測モデルは、さらに明確になった。


                    REQUEST
                       │
                       ▼
                ┌─────────────┐
                │ Access Layer │
                └──────┬──────┘
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
      Returned Result       History State
             │                   │
             ▼                   ▼
      Returned Range        FirstDate
      Returned Bars        BarsCount
      TargetIncluded       Synchronized
             │                   │
             │                   ▼
             │             変化したか？
             │                   │
             └──────────┐        │
                        ▼        ▼
                    比較・分離・検証


そして、

History Expansion

は、

「Request成功」
でも、

「Returned Range変化」
でもなく、

History Stateの観測可能な変化を伴う現象として、
今回の研究では扱っている。


History State
      ↓
  変化あり？
    ↙    ↘
  No      Yes
  ↓        ↓
未観測    Expansion候補

ここで「Expansion候補」は、
History Expansionが確定したという意味ではない。

観測されたHistory Stateの変化を、
次の検証対象として扱うという意味である。


============================================================
16. Level 4のまとめ
============================================================

Level 4では、

「何がHistory Stateを変えるのか？」

という問いに進んだ。

そのために、

・RequestStart
・RequestedBars
・未ロード候補領域へのAccess
・Access Boundary
・Successful Access後

を条件として観測した。

今回の試験条件では、

History Stateの変化を伴う
History Expansionは観測されなかった。

しかし、

「Expansionは起きない」

とは結論しない。

むしろ、

「まだExpansionの条件が捕まっていない」

という状態である。

ここが重要である。

RPBは、

「答えを作る研究」

ではなく、

「観測できたことと、
まだ観測できていないことを分離しながら、
条件を絞っていく研究」

として進んでいる。
